## 0. 결론 요약

1. **v3의 매출 가정은 실제보다 약 5~7배 높다.** v3는 US ARPDAU를 $0.091~0.097로 잡았다. 이 값은 하루 전면 광고 약 5회($18 eCPM 기준)가 있어야 나온다. 그런데 v3 자체 규칙(2판 AND 150초, 세션당 2~3회)에 테스터 행동(8명 중 6명이 데일리가 주력이고, 판 하나에 3~6분)을 넣으면 **DAU당 전면 광고는 하루 약 1.1회**다(§8 몬테카를로). 현실적인 US iOS ARPDAU는 $0.007~0.024(기본값 $0.013)이고, iOS 글로벌 혼합으로는 $0.004~0.014다. 하루 10설치일 때 12개월째 월 매출은 25.5만 원이 아니라 **약 4~6만 원**이다. §1 판정표와 중단선 계산은 다시 해야 한다.
2. **런칭 구성(B)**: 전면은 레벨 사이에만 두고 기준을 "2판 AND 240초"로 바꾼다. 하루 10회, 앱 복귀 후 120초 동안 없음, 데일리에는 0. 보상형은 30분 광고 휴식 하나만 둔다. 배너·앱 오픈·네이티브·보상형 전면·접이식 배너는 모두 끈다. 품질 설정으로 고참여 광고 OFF, 게임 음소거를 SDK에 그대로 전달, 오디오 세션 `.ambient`를 적용한다. 테스터의 삭제 사유 1위는 횟수가 아니라 **소리(8/8)·5초 안에 못 닫음(6/8)·가짜 X(5/8)**였다.
3. **판정 뒤 구성(B+)**: 캐나다·호주·뉴질랜드 판정을 통과하면 **트랙 판 화면에만** 하단 앵커 적응형 배너를 50% 홀드아웃으로 시험한다. 이 게임은 전면 재고가 적어서 배너가 ARPDAU의 약 30%를 차지한다. 모델상 설치 1명당 365일 LTV가 가장 높고(기본값 $0.138, B는 $0.103), 배너 때문에 수명이 24% 넘게 줄지 않으면 B보다 낫다.
4. **공격형(C: 배너 항상 + 매 판 전면)**은 ARPDAU가 B의 2.7배다. 하지만 데일리를 깨고 별점과 공유를 망가뜨린다. 기본 가정에서 LTV가 B+보다 낮고($0.123), 보수 가정에서는 모든 구성 중 가장 낮다($0.042). 분산이 가장 큰 도박이어서 기각한다.
5. **냉정한 순위**: 매출을 좌우하는 것은 ① 설치 수 ② 미디에이션 비딩(+30~60%, 추정) ③ 사업자 등록 뒤 광고 제거 IAP(5/8이 $3~5에 사겠다고 함) ④ 배너(B+) 순이다. 전면 기준을 150초로 할지 240초로 할지는 ±5% 수준이다.

| **전면** | 앱 전환 지점에 둔다. 닫기 지연은 기본 최대 5초, 고참여 동영상은 최대 12초(언론 보도는 15초), 일부 서드파티 비딩 동영상은 최대 30초다. 정책은 아래 §3. | ○. 주력 형식 | Google, 높음(12초 대 15초는 충돌) |

참고: 고참여(high-engagement) 광고는 **앱 단위 설정이고 기본값은 ON**이다. 켜 두면 전면이 최대 12~15초 동안 못 닫히고, 보상형은 최대 60초가 걸리며, 나가는 데 최대 3단계가 필요하다. 이 게임에서는 끈다(§9-4).

### 9-1. `src/ads/policy.ts`

```ts
export const FLAGS = {
  banner: false,          // B+: CA/AU/NZ 판정 통과 후 Remote Config로만 켬. 트랙 판 화면 한정
  appOpen: false,         // 기각 (r6 Yuki·Sophie, 데일리 목적 실행). 경로 삭제 검토
  rewardKeepsake: false,  // 마을 꾸미기 메타 출시 시
  rewardArchive: false,   // 지난 데일리 보관함이 생길 때만
} as const;

export const RULES = {
  graceUnits: 5,
  unitsBetween: 2,              // 하한 2 고정: Remote Config 값이 2 미만이면 2로 clamp ("매 판"은 코드로 불가)
  playSecondsBetween: 240,      // [PLACEHOLDER] 150→240. 허용 범위 [180, 900]
  perSession: 2,
  perSessionLong: 3,
  longSessionMs: 10 * 60_000,
  perDay: 10,                   // 12→10 (240초 기준 40분 플레이)
  resumeQuietMs: 120_000,       // 신규: 30초 이상 백그라운드였다가 돌아오면 120초 동안 전면 없음
  resumeQuietMinBgMs: 30_000,
  afterFullscreenMs: 90_000,    // 신규: 보상형 포함 전면 광고 종료 후 90초 동안 전면 없음
  breakMs: 30 * 60_000,
  breakAfterNthInterstitial: 2,
  streakGiftEvery: 7,
  streakGiftMs: 60 * 60_000,
  sessionGapMs: 30 * 60_000,
  bannerHoldout: 0.5,           // 신규 (B+ 시험 중). 설치 시점에 고정
  // appOpenHoldout / appOpenMinBackgroundMs: 앱 오픈 기각으로 삭제 가능
} as const;
```

- `AdSession`에 `foregroundAt`, `AdState`에 `lastFullscreenAt`과 `bannerHoldout`을 추가한다. `onResume()`은 `backgroundMs ≥ resumeQuietMinBgMs`이면 `foregroundAt = now`로 둔다.
- `Verdict`에 `"resume-quiet"`와 `"cooldown"`을 추가한다.
- `bannerAllowed(s, now, att, screen)`: `screen === "track"` && 플래그 ON && 홀드아웃 아님 && 휴식·선물 아님 && `units > graceUnits` && 설치 당일 아님. `screen`은 `"track" | "daily" | "town" | "settings" | "result" | "guide"`.
- `RULES`·`FLAGS`는 Firebase Remote Config(무료)로 덮어쓸 수 있게 하고, 코드 기본값과 clamp 범위를 함께 둔다. 원격 값이 망가져도 "매 판·데일리 광고"는 불가능해야 한다.
- 테스트(`__tests__/policy.test.ts`)의 150초·12회 기대값(l.31, 40, 57~79)을 갱신해야 한다.

### 9-2. `src/ads/index.ts` · `AdsProvider.ts` · `AdMobAds.ts`

- **배너 화면 상태**: `ads.setScreen(screen)`을 새로 만들고 LanternsScene·Town·SettingsSheet가 호출하게 한다. 지금은 `onUnitComplete` 뒤와 init 때 `showBanner()`를 매번 부른다. 그래서 ① 데일리 유닛 뒤에도 배너가 뜰 수 있고 ② 이미 떠 있는 배너를 다시 요청해 갱신 주기가 초기화될 수 있다. 상태를 기억해서 같은 요청은 무시하게 해야 한다. 또 `watchBreak()`이 배너를 숨긴 뒤 휴식이 끝나도 다시 보이게 하는 경로가 없다. 휴식 종료 타이머가 필요하다.
- **음소거 전달**: `ads.setMuted(m)` → `AdMob.setApplicationMuted({ muted })`. init 때 한 번, 설정 토글 때마다 부른다. Google 문서에 따르면 음소거하면 동영상 광고 대상이 줄어 매출이 떨어질 수 있다. 하지만 이 앱에는 실제 음소거 컨트롤이 있으니 그 상태를 정확히 반영하는 것이 맞다. 대가는 감수한다.
- **보상형 지점별 광고 단위**: `showRewarded(placement: "break" | "keepsake" | "archive")`, `prepareRewarded(placement)`. 지점마다 광고 단위를 따로 두면 리포트와 플로어를 분리해 볼 수 있다.
- **배너**: `BannerAdSize.ADAPTIVE_BANNER`, `BOTTOM_CENTER`, 수직 여백 4~8pt `[PLACEHOLDER]`. `BannerAdPluginEvents.SizeChanged`로 높이를 받아 Phaser 레이아웃(`geo` 계산의 하단 안전 영역)에 반영한다. **배너가 웹뷰 위에 떠서 캔버스를 덮으면 안 된다**(플러그인 README).

### 9-3. 전면 표시 시점 이동 (`LanternsScene.ts`, 담당 U)

지금은 `endFinale()`이 다음 판을 올린 **뒤** `adsApi.onUnitComplete`를 부르고, 광고는 새 판 위에 뜬다. 이것은 정책의 "새 화면이 뜬 직후 전면 금지"와 실수 클릭 위험(피날레를 탭으로 넘긴 직후)에 걸린다. 제안:

1. `startFinale()`에서 `ads.recordUnit(u)`를 부른다(동기 판정, 표시는 하지 않음).
2. 피날레의 "옛 판 나감(`outAt`) → 새 판 들어옴(`inAt`)" 사이에서 `ads.breakPoint()` → `"show"`이면, 다음 판 생성 대기에 쓰는 기존 `hold`를 그대로 써서 광고를 띄운다. 광고가 닫힌 뒤 새 판을 슬라이드로 넣는다.
3. 사용자가 탭으로 넘긴 경우에는 마지막 입력에서 최소 400ms `[PLACEHOLDER]`가 지난 뒤에 광고를 띄운다.
4. 휴식 칩은 새 판이 들어온 뒤에 띄운다(현행 8초 유지).

#### 9-5b. 테스트 광고 / 실제 광고를 정하는 규칙 (2026-10-19)

- 웹 번들은 모든 구성이 같다(`build:m1`; App Store 아카이브도 `--mode m1`). 그래서 `import.meta.env.MODE`로는 구분할 수 없다(이걸 쓰면 앱스토어 빌드가 영원히 테스트 광고를 낸다). 구분 신호는 **네이티브 빌드 종류**뿐이다.
- `AdAudio.buildKind()`(`ios/App/App/AdAudio.swift`) → `{ release }`. `DEBUG`, `PERF_PROBE`(Debug/Measure 구성), 시뮬레이터이면 `false`, 그 외(Release 구성, 실제 기기)이면 `true`. JS는 `src/native/adAudio.ts`의 `isReleaseBuild()`.
- `src/ads/AdMobAds.ts` `adsAreTest(testing, release)`: **실제 광고는 `config.testing === false` 그리고 `release === true`일 때만**. 웹/e2e/개발, 네이티브 호출 실패(오류·구버전 셸), 아직 모름(null)은 전부 테스트 광고(fail-safe, 실패는 `[ads] build kind unavailable` 1회 경고).
- 빌드 종류는 `start()`에서 SDK `initialize`보다 먼저 한 번 확정한다. 그 전에는 전면/보상형/배너 어떤 요청도 나가지 않는다(`live()` 가드, `src/ads/__tests__/testMode.test.ts`).
- `scripts/release-gates.mjs`가 `AdMobAds.ts`의 `import.meta.env` 사용, `isReleaseBuild()` 호출 누락, `buildKind`의 PERF_PROBE 분기 훼손을 막는다(`npm run ios:release-check`).
- 확인: Debug 시뮬레이터 빌드 로그에 `[ads] buildKind release=false`(첫 수 이후)가 찍히면 테스트 광고 경로다.

## 10. 출시 뒤 A/B 시험과 중단 지표

**검정력 경고 (먼저 읽을 것)**: D7 18%에서 2%p 차이를 검정력 80%, α 0.05로 잡아내려면 **한쪽 약 5,500명**이 필요하다. 하루 10설치 50/50이면 약 3년이다. 5%p(상대 28%) 차이도 한쪽 약 820명, 164일이 걸린다. 따라서 D1·D7은 **큰 피해를 걸러내는 안전장치**로만 쓴다. 주 판단은 관측 단위가 많은 지표로 한다. ① 광고 1회당 지표(광고 뒤 이탈률: 하루 노출 약 150건) ② 사용자-일 지표(하루 트랙 판, 하루 플레이 분) ③ ARPDAU. 하루 설치 50건 미만이면 사전 등록한 순차 판정(베이지안, 넓은 사전분포)으로 진행한다.
