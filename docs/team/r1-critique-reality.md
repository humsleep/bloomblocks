# R1 교차 비판 — Reality Checker (2026-10-17)

대상 문서: `r1-market.md`, `r1-design.md`, `r1-visual.md`, `r1-aso.md`, `r1-growth.md`. Wick v2 그림은 `playtest/shots/wick-v2/`의 01, 05, 10번을 직접 열어 봤다.

먼저 칭찬할 점이 있다. 다섯 문서 모두 "AI 페르소나는 사람 데이터가 아니다", "미국 1위는 사실상 0 %"를 스스로 적었다.

문제는 그다음이다. 다섯 문서가 각자 **출시 전 할 일**을 늘렸고, 그 합이 사람 테스트 0명인 상태에서 **에이전트 일로 약 50–60일과 사용자 주당 5–6시간**이 됐다.
- design 30일(그중 출시 전 13.5일)
- growth 출시 전 필수 11–16일
- visual Wick 6.5일(design 30일과 일부 겹침)
- ASO: 메타데이터 17개 로캘, 8개 언어 프리뷰, CPP
- market: 숏폼 하루 3편, FI·DK 현지화

이번 라운드의 결론은 하나다. **사람 데이터가 나오기 전에는 이 목록을 줄이는 쪽으로 결정한다.**

## 1. 가장 약한 주장 5개

### W1. 같은 숫자인데 문서마다 값이 9배까지 다르다: "작은 상점 퍼즐 1위에 필요한 하루 설치"

| 상점 | market (Sensor Tower 자동 요약, 2025 Q4) | ASO (UK × 인구비) | growth (2019 US × 인구비) |
|---|---|---|---|
| NZ | 약 890 | 400–3,000 | 약 2,400 |
| IE | **약 260** | 400–3,000 | 약 2,400 |
| IS·LU | 20–80 | — | 170–300 |

- 세 값이 모두 **출처 하나에 인구비 같은 근사를 곱한** 추정이다. 어느 것도 Duskwick의 계획을 받칠 만큼 단단하지 않다.
- 같은 사실도 엇갈린다. Meowdoku 출시일을 market은 05-19(RSS), growth는 05-04로 적었다. 1위 유지 기간도 design은 약 30일, market은 순위 이력으로 따로 적었다.
- **채택하지 않는다.** 다음 행동은 market 담당이 IE·NZ·DK의 순위와 하루 설치 관계를 **실측 앵커 2개 이상**으로 다시 정하는 것이다.
  - 앵커 예: 개발자가 공개한 "출시일 IE n위 = 하루 m 설치" 사례. 또는 출시 뒤 우리 앱의 ASC 설치 수와 그 시각의 RSS 순위 쌍.
  - 그 전에는 "IE 1위 시도"를 일정에 넣지 않는다.

### W2. ASO §5.1 "ASO만으로 하루 10–40건(기본 20)"
- 근거는 자동완성에 검색어가 있는지(대리값)에 "검색어마다 하루 수십 회"(추정)와 "검색 → 다운로드 20–30 %"(추정)를 곱한 것이다. 세 항이 모두 추정이다.
- v4의 사전 분포는 하루 2건 미만이 45 %, 20건 이상이 10 %다. 이 문서는 새 데이터 없이 기본값을 v4 상위 10 % 구간으로 옮겼다.
- 검색 인기도(Apple Ads 5–100)는 계정이 없어 보지 못했다고 문서 스스로 적었다.
- 같은 문서의 메타데이터 현지화 비용 "언어당 약 1시간"도 낮게 잡혔다. 17개 로캘에 원어민 확인과 키워드 반복까지 하면 로캘당 반나절 이상으로 본다(판단).
- **채택하지 않는다.** 출시 뒤 ASC 출처 유형 중 "App Store 검색"의 실측 설치로만 판정한다.

### W3. visual: "B+ 채택" 근거가 자기 채점이고, 자기 목업에 결함이 보인다
- 귀여움 8.3, 홈 화면 8.0, 유치함 3.4는 **디자인한 모델이 직접 매긴 페르소나 점수**다(문서도 자기 편향을 인정한다).
- IoU 오독 테스트도 비교 원형(양파, 만두, 유령, 불 요정)을 같은 에이전트가 그렸다. B+ 0.76과 B 0.84의 차이는 원형을 어떻게 그리느냐에 따라 뒤집힐 수 있다. 문서 스스로 "그냥 타원도 만두와 0.90"이라고 적었다. 즉 이 지표는 판별력이 없다.
- 직접 확인한 결함 [화면]
  - `05-in-app-board-faces.png`, 충돌 장면: 히어로 Wick의 불꽃이 오류 띠 글자 "s|hine" 위에 겹쳐 그려진다. 띠 위로 문패 조각이 삐져나오는 R1 결함도 그대로다.
  - 같은 파일, 완성 장면: Wick이 문패 "1"을 가린다. "Solved!"가 숫자 2를 덮고, "Next house"가 4행을 덮는다.
  - `10-store-hero`: Wick이 HUD의 "How to"를 가린다(화면에 "ow to"만 보임). 게임에 없는 친구(Momo)가 등장한다. **앱에 없는 캐릭터와 기능을 스토어 샷에 넣으면 2.3.3과 2.3.7 위험이 있다**(growth 문서도 같은 지적: "실제 게임에 없는 캐릭터로 영상을 찍으면 기대 불일치").
- "콜드 스타트 영향 없을 것"은 측정하지 않은 값이다.
- **방향만 조건부로 채택한다**(§2의 A6). 점수와 IoU는 결정 근거에서 뺀다.

### W4. design Top 10: 판단을 나눗셈으로 정밀해 보이게 만들었다
- "효과 1–5"는 판단값인데 이것을 노력으로 나눠 6.0, 1.33, 0.86 같은 소수 순위를 만들었다. 입력이 판단이면 출력도 판단이다.
- **출시 전 13.5일, 전체 30일**을 사람 데이터 0명 상태에서 배정했다. 같은 문서가 곡선 조정을 "사람 데이터 전에는 동결"하라고 하면서 메타는 먼저 짓자고 한다. 앞뒤가 맞지 않는다.
- §5는 측정 수단을 "Firebase 무료 이벤트"로 적었고, §4는 "A/B 플래그로 확인"이라고 했다.
  - 지금 클라이언트에는 분석 SDK가 0개다(grep). Firebase를 넣으면 App Privacy 답변과 PrivacyInfo가 바뀌고 콜드 스타트를 다시 재야 한다. 이 비용이 노력에 들어 있지 않다.
  - A/B는 인프라가 없어서 지금은 할 수 없다.
- 친구 해금 규칙이 visual과 충돌한다.
  - design: 데일리를 푼 날의 **누적** 수. 끊겨도 줄지 않는다.
  - visual: "3일 **연속**", "7일 **연속**". 끊기면 못 얻는다.
  - 두 문서가 같은 시스템을 반대 원칙으로 설계했다.
- "코어는 이미 상위권(막힘 피드백 8/10)"도 페르소나 점수다.
- **채택하는 것**: #1 별점 요청, 곡선 조정 동결, 7일 선물 폐기(광고 회의 안건으로). 나머지 메타(친구 레일, 달력, 고르는 골목, 축제)는 **TestFlight 결과 뒤로 보류**한다.

### W5. growth: k-factor와 시나리오 확률은 추정 네 개의 곱이다
- k = s × r × c × L에서 s 0.05, r 15–50, c 0.002 → 0.01–0.015는 모두 추측이다. 결과 "0.1–0.35"는 추측의 곱이라 정밀해 보일 뿐이다. 시나리오 확률(50–55 / 30 / 10–12 / 3 %)도 근거로 고정된 값이 없다.
- 노력을 낮게 잡았다.
  - 웹 데일리 5–8일: 별도 빌드, 시간대별 날짜 전환, GitHub Pages(사용자 계정), 웹용 개인정보 문구, Smart App Banner, 웹에서 같은 코어 바이트를 검증하는 테스트까지 넣으면 그 이상으로 본다(판단).
  - 사용자 주 5–6시간 + SNS 계정 5개 개설은 1인 개발자의 실제 비용이다. 이것이 v4 W8 판정(DAU 80)과 맞는지 계산하지 않았다.
- "T−8주에 Wick을 게임에 넣는다"가 모든 콘텐츠의 선행 조건이다. 그러면 출시가 최소 8주 밀린다. 그 결정은 사용자가 해야 한다.
- 좋은 점: 엽서 목업(`03-result-postcard`)이 정답 등불 위치를 보여 줘 **스포일러**가 된다는 지적은 정확하다(사실 확인 가능).
- **채택하는 것**: P-1(링크와 ct 토큰), P-3의 스포일러 제거, P-9(별점), 사전 주문과 피처링 지명. **보류하는 것**: 웹 데일리는 FTUE 게이트를 통과한 뒤로, 콘텐츠 운영은 사용자 결정 뒤로.

## 3. TestFlight 사람 테스트 프로토콜 (바로 구현할 수 있는 수준)

### 3.1 목적과 판정
- 이번 테스트로 답할 질문은 두 가지다.
  1. 처음 보는 사람이 혼자 규칙을 배워 1판을 끝내는가(FTUE).
  2. 다음 날 스스로 다시 여는가(D1 대용).
- 합격선(사전 등록):

| 지표 | 정의 | 합격선 |
|---|---|---|
| M1 튜토리얼 완료 | `tut_end` / `first_open` | ≥ 90 % |
| **M2 FTUE** | 세션 1 안에 gentle 1을 **힌트 0회로** 완성 | **≥ 80 %** |
| M3 첫 완성 시간 | `first_open` → gentle 1 `board_end` 중앙값 | ≤ 180 s |
| M4 힌트 | gentle 1–3 판당 평균 힌트 | ≤ 1.0 |
| M5 규칙 이해 | 설문 자유 서술을 4개 규칙 채점표(빛은 돌에서 멈춤 / 서로 비추면 안 됨 / 숫자는 상하좌우 등불 수 / 모든 칸을 밝힘)로 채점 | 3/4 이상인 사람 ≥ 70 % |
| **M6 D1 대용** | 첫 실행 다음 현지 날짜에 `app_open`이 있음(알림·연락 없이) | **≥ 35 %** |
| M7 3일 데일리 | 1–3일차 중 2일 이상 `daily_end` | ≥ 20 % |
| M8 안정성 | TestFlight 크래시 / 세션 | 0건(세션 ≥ 200) |

- 판정 규칙
  - M2 < 60 % → **모든 기능 작업을 멈추고** FTUE만 고친다.
  - 60–80 % → 혼란 상위 3개를 고친 뒤 재테스트.
  - ≥ 80 % → 보류 목록을 다시 연다.
- 한계: n = 20, 80 %의 95 % Wilson 구간은 약 [58, 92] %다. 그래서 n = 30을 목표로 하고, 지인과 낯선 사람을 **따로** 집계한다. 지인은 더 참을성 있고 더 호의적이다.

### 3.2 표본과 모집 (n: 완주자 30명 목표, 모집 50명)
- 할당
  - 35–54세 여성 중 논리 퍼즐 비경험자 ≥ 12명
  - 한국어 사용자 ≥ 8명, 영어 사용자 ≥ 12명
  - 오래된 기기(iPhone XS–11, SE 2) ≥ 3대
  - iPad 사용자 ≥ 2명
- 무료 채널(사용자가 직접 한다)
  1. 카카오톡 가족·지인·직장 단톡(내부 테스트 100명 한도, 심사 없음, Apple ID 이메일 필요)
  2. 지역 맘카페와 취미 카페(게시 규칙 확인)
  3. Facebook 퍼즐·cozy 그룹(관리자 허락 뒤)
  4. r/TestFlight, r/playmygame, r/CozyGamers(규칙 확인. r/iOSGaming은 개발자 홍보를 중단했다는 보고가 있다: growth §2-1)
  5. Thinky Puzzle Discord
- 외부 테스트는 공개 링크를 쓴다. 첫 빌드는 Beta App Review(보통 1–2일)를 거친다.
- 금지: 금전·기프트 보상, "좋은 리뷰" 요청. 감사 표시는 크레딧(설정에 테스터 이름)만 한다.
- 선행 조건(사용자): ASC 앱 레코드 생성, 테스트 정보(연락 이메일, 피드백 안내) 입력.

### 3.3 과제 (테스터 안내문에 그대로 넣는다)
- **0일차**: "앱을 열고 10분 정도 자유롭게 해 보세요. 누구에게도 방법을 묻지 마세요. 끝나면 그냥 닫으면 됩니다."
  - 규칙 설명, 스크린샷, 동영상을 미리 보여 주지 않는다.
- **1–2일차**: 아무 연락도 하지 않는다(D1 대용 지표를 오염시키지 않기 위해서다).
- **3일차**: 메시지 1회. "설정 > 베타 로그 보내기"를 누르고 설문(Google Forms, 무료, 5분)에 답해 달라고 한다. 설문 문항:
  1. 이 게임의 규칙을 친구에게 설명하듯 한두 문장으로 써 주세요(M5).
  2. 가장 헷갈렸던 순간은?
  3. 광고가 어떻게 느껴졌나요(1–5, 테스트 광고 표시 포함)?
  4. 계속 하고 싶은 정도(1–5)와 이유.
  5. 화면에 보인 로그 ID(아래 `tid`)를 적어 주세요.
- **관찰 세션 5명**(0일차, 화상통화 화면 공유나 대면): 말하면서 하기(think-aloud). 관찰자는 개입하지 않는다. NOVICE-TEST C1–C31 체크표에 시각을 기록한다.

### 3.4 TestFlight 빌드 전용 로컬 이벤트 로그 (서드파티 SDK 없음)
- **빌드 분리**
  - `vite build --mode beta`일 때만 `import.meta.env.VITE_BETA_LOG === "1"`로 `src/beta/log.ts`를 지연 import한다. 프로덕션 번들에는 들어가지 않는다(트리 셰이킹).
  - `scripts/check-no-probe.sh`에 `betaLog`, `beta/events` 문자열 검사를 추가해 **Release 아카이브에 있으면 실패**하게 한다.
  - `ios:release-check`에도 같은 게이트를 넣는다.
- **저장**
  - Capacitor Filesystem의 `Directory.Data/beta/events.jsonl`에 한 줄 JSON씩 append한다.
  - 2,000줄 또는 256 KB를 넘으면 앞 절반을 버린다.
  - 쓰기는 `requestIdleCallback`이나 500 ms 디바운스 버퍼로 한다. 첫 프레임 전에는 쓰지 않는다(콜드 스타트 경로 0).
- **식별자**
  - 첫 실행 때 무작위 6자 `tid`를 만들어 설정 화면의 로그 버튼 옆에 보여 준다. 설문과 맞추는 용도다.
  - IDFA·IDFV·기기명·이메일은 넣지 않는다.
- **레코드**: `{"v":1,"tid":"k3x9qa","d":"2026-10-20","s":3,"ms":41250,"e":"board_end","p":{…}}`
  - `d`: 현지 날짜(D1 계산용)
  - `s`: 세션 번호(포그라운드 복귀 30분 이상이면 +1)
  - `ms`: 세션 시작 기준 경과 ms. 벽시계 시각은 넣지 않는다
- **이벤트 21종** (`p`에 들어가는 값)
  - `first_open` · `app_open{cold, ttiMs}` · `app_bg`
  - `tut_step{step, wrong}` · `tut_skip{step}` · `tut_end{ms, wrongTotal}`
  - `board_start{track, n, w, h}` · `board_end{track, n, ms, moves, undos, hints, errs:{conflict, over, zero, stuck}}` · `board_quit{track, n, ms, lit%}`(풀지 않고 백그라운드)
  - `hint{level}` · `band{kind}` · `stone_tap`
  - `howto_open{from}` · `settings_open` · `town_open`
  - `daily_open` · `daily_end{ms, hints}` · `result_action{continue|share|close}`
  - `ad{kind, shown, dismissMs}` · `consent_shown` · `notify_prompt{answer}`
  - `js_error{hash}`(메시지 해시만)
- **보내기**
  - 베타 빌드의 설정 맨 아래에 "베타 로그 보내기" 줄을 둔다.
  - 누르면 파일을 `@capacitor/share`(이미 의존성에 있음)로 넘기고, 테스터가 메일이나 카톡으로 보낸다.
  - 자동 전송, 네트워크 호출, 서버는 없다. 그래서 App Store용 App Privacy 답변은 바뀌지 않는다(릴리스에 코드가 없음).
  - 안내문에 "기록 내용: 판 진행과 탭 횟수, 개인정보 없음"을 적는다.
- **분석**
  - `playtest/beta/analyze.mjs`가 받은 jsonl 파일들을 읽어 M1–M8을 테스터별·전체로 표로 낸다.
  - 혼란 지점은 세션별 마지막 이벤트 분포(이탈 직전 화면)로 본다.
- **노력**: 로그 모듈과 21개 호출 지점 1일, 보내기 줄과 게이트 0.5일, 분석 스크립트 0.5일. 합계 약 2 에이전트일.
- **검증**
  - e2e: 베타 모드에서 튜토리얼과 1판을 끝내면 이벤트 순서를 스냅숏으로 비교한다.
  - Release 빌드에서는 `check-no-probe` 실패 대조군을 확인한다.
  - 실기기 M1 p75 변화가 없는지(±20 ms) 확인한다.

### 3.5 일정
- D0: 사용자가 ASC 레코드를 만든다 → 베타 빌드를 업로드한다 → 내부 테스터 10명.
- D1–2: 외부 Beta App Review를 거쳐 공개 링크를 연다 → 모집 글을 올린다.
- D2–9: 테스터마다 0–3일차를 진행한다. 관찰 세션 5회.
- D10: `analyze.mjs` 결과로 판정 회의를 연다(§3.1 규칙). 결과는 `playtest/BETA-R1.md`에 적는다. 사람 데이터이므로 AI 페르소나 결과와 섞지 않는다.
