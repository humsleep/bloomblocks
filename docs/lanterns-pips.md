# Lanterns 변형 P("pips") — 숫자 돌(Akari) 규칙·생성기

플레이테스트 실험용 변형. 기존 `games/lanterns`(B1)와 픽스처는 건드리지 않는다. 구현: `games/lanterns-pips/`
(`rules.ts` 규칙, `level.ts` 텍스트, `solver.ts` 정확 해 개수, `deduce.ts` 단계 추론 + 사람 흉내 봇, `generator.ts`,
`tracks.ts` 두 트랙·데일리, `tricks.ts` 요령 서명·외딴 한 칸, `analysis.ts` 보드 판독·범인, `hint.ts` 힌트 엔진, `share.ts` 데일리 번호·공유 문구).
gameId = `GAME_ID.lanternsPips` = 5. 수 인코딩(1바이트 = stride-8 칸 인덱스)은 lanterns와 같다.

## 규칙

- 보드·빛·충돌은 lanterns와 같다(`docs/lanterns-rules.md`). **예산 없음.**
- 일부 돌에 숫자 0–4: 그 돌의 상하좌우 칸에 놓인 등불 수가 **정확히** 그 숫자.
- 완료 ⇔ 모든 바닥 켜짐 ∧ 충돌 0 ∧ 모든 숫자 일치. 완료 후 모든 수는 불법(`null`).
- 레벨 텍스트: `#` 돌, `0`–`4` 숫자 돌, `.` 바닥, `L` 해답 오버레이.
- `stateBytes` 60바이트 LE: `w h 숫자돌개수 0 | stones lo hi | numbered lo hi | lanterns lo hi | 숫자 니블 32바이트`
  (칸 i → 바이트 `28 + (i >> 1)`, 짝수 i는 하위 니블; 숫자 없음 = `0xF`).

## 추론 단계(난이도)

- T1 숫자 돌: 이미 n개면 나머지 이웃 표시(0 포함), 남은 후보 = 필요 수면 모두 배치.
- T2 어두운 칸을 밝힐 수 있는 자리가 하나뿐 → 배치.
- T3 한 단계 모순: 후보 q에 놓으면 **즉시**(연쇄 없이) 어떤 숫자가 불가능/초과하거나 어떤 어두운 칸의 후보가 0 → q 표시.
- 모든 규칙이 건전하므로 단계로 풀리면 해는 유일하다.

## 생성기 (`generatePips`, `levelForIndex` — 1차 플레이테스트용 레거시 스트림, 출력 불변)

돌 배치(밀도 5×5 16–24 %, 6×6 17–26 %, 7×7 18–28 %, 대칭 rot180 ½ · mirror ¼ · 없음 ¼) → 구조 필터(분리 바닥, 고립 칸,
36 % 초과 빈 직사각형) → 무작위 완전 해 → 모든 돌에 숫자 → 유일하지 않으면 버림 → 숫자를 무작위 순서로 하나씩 제거,
**정확 솔버로 유일** ∧ **태그 단계 상한 이내로 풀림**(intro/easy T2, 나머지 T3)일 때만 제거 확정 → 사람 흉내 봇 8회(+24회 확인)
→ 중앙값이 밴드(`PIPS_BANDS`) 안이면 채택, 아니면 가장 가까운 후보(최대 120회 시도). 곡선: 1–5 5×5, 6–14 6×6, 15+ 7×7,
태그 주기 mid, mid+, hard, easy, mid(1–2는 intro). 시드 키 `lanterns-pips:free:g1:<n>`; 출력이 바뀌면 `PIPS_GENERATOR_VERSION`을 올린다.

## 시간 모델 (`PIPS_TIME`)

배치 4 s, 제거 2 s, 막힘 6 s(lanterns `TIME_MODEL`과 같은 바탕) + T2 발견 2 s, T3 모순 6 s, 헛된 T3 시도 1 s.
봇은 T1 우선, T1이 없을 때 15 %(‰ 150) 확률로 깊게 보지 않고 추측(가장 제약된 어두운 칸 후보, 보이는 숫자 초과 금지),
모순/막힘이면 추측 이후 등불을 모두 걷고 그 칸을 표시한다.

도구: `npm run gen:stats:pips -- --count 200`, `npm run depth -- --levels`(N/P/E 깊이 사전 점검, `scripts/depthCheckLib.ts`).

## 공통 생성 게이트 (모든 스트림)

- **유일성 게이트**: 숫자 제거가 끝난 최종 보드를 정확 솔버(`countSolutions`, 노드 상한 `UNIQUE_GATE_NODES` = 2,000,000)로
  다시 센다. 해가 1개가 아니거나 탐색이 상한에 걸리면 그 후보는 버린다. 반환 직전에도 한 번 더 확인하고, 실패하면 예외를 던진다
  (유일하지 않은 보드는 절대 반환되지 않는다). rng를 쓰지 않으므로 레거시 스트림 출력은 그대로다.
- 선택 파라미터(트랙·데일리만 사용): `requireT3`(T1–T2만으로 풀리면 버림), `tailMax`(봇 꼬리 ~p88 초과분을 밴드 거리에 더함),
  `solutionPicks`(무작위 완전 해를 k번 뽑아 등불이 가장 많은 것을 씀 — 길게, 깊지 않게), `opening`(아래),
  `t2 {lo, hi}`(숫자 제거는 `grade.t2` ≤ hi일 때만 확정, 변환 후 최종 보드의 t2가 범위 밖이면 버림),
  `zeroMaxPct`(0 숫자를 제거 순서 앞으로 — rng 추가 사용 없음 — 그래도 0이 그 비율을 넘으면 버림),
  `startVisible`(빈 보드에서 바닥 이웃 수 = 숫자인 0 아닌 숫자 돌이 없으면 버림; `startCells(level)`).
  `trick {mod, want}`(아래 "요령 회전"). 거절 사유에 `t2Range`, `zeros`, `noStart`, `trick`이 추가됐다.
- **제거 루프의 유일성(라운드 6)**: 숫자 하나를 지울 때 정확 솔버를 다시 돌리지 않는다. 단계 규칙은 모두 건전하므로 tier-solvable ⇒ 유일하고,
  T1+T2 판에서 솔버의 전파(= T1+T2)는 분기하지 않아 상한에 걸릴 수 없다. 모든 숫자를 가진 판도 `grade`가 먼저 보고, 실패할 때만 솔버로 사유를
  가른다(`notUnique`/`solverLimit`/`tooDeep`). 레거시·deduce 출력은 바이트 단위로 같다(deduce 1–200·레거시 카나리 확인). 마지막 유일성 게이트는 그대로.
- **유한 탐색 `search`(라운드 6, PERF-1; `PipsSearch`, gentle 21+와 데일리만)**: 라운드 5의 gentle 50(마무리 판)은 14,976회 시도·3.5–6 s(부하 시
  19.6 s)에 밴드도 놓쳤다 — 조건(T2 ≥ 7 ∧ 오프닝 버킷 ∧ 요령 버킷 ∧ 외딴 한 칸 ≤ 2)을 다 맞는 판이 0.04 %라 시도 상한까지 돌았다.
  - 해 고르기 `score`: `solutionPicks`개의 무작위 완전 해를 점수순으로(동점은 뽑은 순서, rng 추가 사용 없음) — `lanterns`(등불 수),
    `free`(돌에 닿지 않는 등불 수 → 등불 수; 그런 등불은 숫자로 놓일 수 없어 반드시 T2 단계), `sum`(둘의 합 → 등불 수). 모든 숫자로
    tier-solvable이고 T2 ≤ 상한인 첫 해를 쓴다(예전에는 해 하나가 안 되면 배치 전체를 버렸다).
  - `bigFirst`: 제거 순서를 큰 숫자부터(섞은 뒤 안정 정렬) — T1으로 등불을 놓는 숫자가 먼저 빠져 T2가 늘어난다.
  - 오프닝 보존: gentle(오프닝 비어 있으면 안 됨)은 마지막 여는 숫자를 지우지 않는다(빈 오프닝은 8개 변환 모두 실패).
  - 변환 고르기: 내놓을 변환의 **자기 T2 수**(= 요령 서명 경로 길이)도 [t2.lo, t2.hi] 안이어야 한다(T2 수는 변환마다 ±1 달라진다).
  - `scoredMax`: 봇까지 돌린 후보가 이만큼이면 멈추고 가장 가까운 것을 낸다(밴드 안이면 즉시).
  - **단계적 완화(무한 루프 없음)**: 후보가 하나도 없을 때만 `maxAttempts / 4`회마다 한 단계씩 — 1 요령 버킷 해제, 2 + 오프닝 버킷 해제(비어 있지 않음은 유지),
    3 + T2 하한 − 1, 4 + T2 하한·오프닝·외딴 한 칸 제한 없음. 시도 상한 2 × `maxAttempts`. `meta.relaxed` = 낸 판의 단계(테스트: gentle 1–300,
    데일리 120일(+퍼즈 800일) 모두 0). 완화도 결정적이다(시도 번호로만 정해진다).
  - 속도: 제거·채점의 할당 없는 경로(`applyFirstT1`, `firstT2`, 광선 재사용, `randomSolution` 할당 제거 — 같은 rng 소비·같은 결과)로 시도당 약 2배 빠르다.
  이 파라미터가 없으면 출력은 이전과 같다(레거시·데일리·deduce 불변). `meta.trick` = 내놓은 보드의 요령 서명.
- **오프닝**: `openingCells(level)` = 빈 보드에서 T1만 고정점까지 적용했을 때 놓이는 등불 칸 집합(칸 인덱스, 오름차순).
  같은 오프닝 ⇔ 이 집합이 같음(보드 크기 무관). 생성기는 보드를 2면체 변환 0..7(항등, 90°, 180°, 270°, 좌우, 상하, 전치, 반전치) 중
  `FNV-1a(오프닝) mod 10 = want`인 첫 변환으로 내놓고, 없으면 버린다. 트랙은 want = n mod 10, 데일리는 want = 일 번호 mod 10이므로
  **10레벨(10일) 창 안에서 오프닝이 절대 반복되지 않는다**. 변환은 유일성·단계·난이도를 바꾸지 않는다.
- **요령 회전** (`tricks.ts`, gentle만): 요령 서명 = 결정적 T1+T2 풀이 경로(`grade(level, 2)`와 같은 순서)에서 쓰인 T2 단계 종류의
  다중집합. 종류 = 모양 × 원인: 모양 `self`(칸이 자기 자리에서만 밝혀짐), `boxed`(칸의 행 또는 열 구간이 자기 하나 — 돌 사이에 갇혀
  다른 축의 한 곳에서만 밝혀짐), `line`(그 밖: 열린 줄 끝에서 밝혀짐); 원인 = 다른 자리들이 빠진 이유 `light`(빛), `mark`(숫자),
  `mixed`(둘 다). 서명 문자열 예 `self-light×2 boxed-mixed×1`(T2가 없으면 ""). 버킷 = (종류 코드 합) mod 5(`TRICK_WINDOW`), 코드는
  `TRICK_KINDS` 순서 1–9(흔한 네 종류가 1–4라 T2 0–1단계인 초반에도 다섯 버킷이 다 나온다). 레벨 n은 버킷 = n mod 5만 받는다
  (오프닝 변환과 함께 8개 변환 중에서 고름; 없으면 버림). 같은 서명 ⇒ 같은 버킷이므로 **연속 5레벨 안에서 서명이 절대 반복되지
  않는다**("직전 4레벨과 같으면 거절"보다 강하다). 레벨이 앞 레벨에 의존하지 않아 `levelForTrack(n)` 임의 접근이 그대로 O(1)이다.

### 라운드 7 (페르소나 라운드 6): 0 돌과 "진짜" T2 — gentle 21+ g7(`GENTLE_RAMP_VERSION` = 7)

r6에서 8/8이 "마무리 판 J-40이 큰 판이 아니다"라고 했다. J-40은 T2 8단계(가장 많음)였지만 0 돌 6개가 만든 단계는 사람에게 공짜였다.

- **진짜 T2(`realT2(grade)` = `t2 − t2zero`, `deduce.ts`)**: 결정적 T1+T2 경로(`grade`)에서 T2 단계(어두운 칸 c를 자리 q 하나로만 밝힘)가 **0 돌에 기댄다** ⇔

  그런 단계 수가 `Grade.t2zero`이다. 데이터: r6 J-40 t2 8 / 진짜 1, J-33 t2 6 / 진짜 3 — 테스터 판정(40이 33보다 쉽다)과 맞는다(테스트 고정).
  "다른 자리가 **모두** 0 표시"(좁은 정의)는 J-40 진짜 5 = J-33 진짜 5로 테스터 판정을 설명하지 못해 쓰지 않았다.
- **gentle 21+ 규칙**: `t2` 범위 = **진짜 T2**(제거 상한·하한·변환 검사 모두, `PipsSearch.realT2`). 0 돌 상한 `GENTLE_ZERO_MAX` 3, 마무리 판 `GENTLE_FINALE_ZERO_MAX` 2

### 보드 판독 (`analyzeBoard`)

- `lit`/`litBy`: 칸별 0/1, 칸을 비추는 등불 수(등불은 자기 칸도 비춘다; 2 이상 = 이중 조명). `litCount`/`floorCount`는 바닥 칸만.
- `conflicts`: 서로 보는 등불 쌍 [a, b] (a < b), 오름차순.
- **합법 추가 등불** q: 바닥, 등불 없음, 어둡다(밝은 칸에 놓으면 충돌), q에 붙은 숫자 돌 중 이미 찬 것(have ≥ need)이 없다
  (= 놓으면 그 숫자를 넘치게 하지 않는다).
- `stones`(숫자 돌만): over(초과), ok(정확 — 0 돌은 주변 등불이 없을 때만), blocked(부족한데 합법 빈 이웃 수 < 남은 필요 수,
  0개 포함), under(부족, 아직 가능). "숫자 맞음" 카운터는 없다.
- `blocked: Array<{ cell; by: 'light' | 'stone'; stones: number[]; lanterns: number[]; causes: Array<'light' | 'stone'> }>`:
  어두운 바닥 중 자기 행·열 구간(자기 포함, = 후보 자리) 어디에도 합법 추가 등불을 둘 수 없는 칸, 칸 오름차순. **원인을 모두** 준다
  (라운드 3: 8명 중 7명이 실제 원인인 자기 등불의 빛 대신 돌로 안내됐다).
  - `lanterns`: 후보 자리 중 **빛 때문에만** 빠진 자리(밝음 ∧ 찬 숫자 돌에 붙지 않음 — 빛이 없었다면 이 칸을 밝힐 수 있었던 자리)를 비추는
    놓인 등불, 오름차순. 밝은 후보가 모두 찬 숫자 돌에도 붙어 있으면 밝은 후보를 비추는 등불 전부(빛도 원인의 반이므로).
  - `stones`: 어두운(빛으로는 가능한) 후보를 막는 찬 숫자 돌, 오름차순(이전과 같은 정의). 어두운 칸은 자기 자신이 항상 그런 후보이므로
    `stones`는 비지 않는다.
  - `causes`: `'light'`(lanterns ≠ []) 다음 `'stone'`(stones ≠ []). `by` = lanterns ≠ []이면 `'light'`(더 바로 고칠 수 있는 원인), 아니면 `'stone'`.
  - 회귀(라운드 3 실제 상태): J-15 `B3`(돌 A3·C3 사이, 남은 자리 B1을 E1 등불이 비춤) → `lanterns` = [E1, C2, A5] (E1 포함),
    `stones` = [A3, C3, A6]; W-4 `B6`(0 돌 C6, 자리 A6·B5를 A5가 비춤) → `lanterns` = [D4, A5], `stones` = [C6]. 정의상 맞는 등불(C2, A5,
    D4)도 함께 나온다 — 어느 것이 틀렸는지는 해를 아는 힌트(`removeWrong`)만 말한다. UI는 `lanterns`를 "길을 막는 빛"으로 강조하고
    틀린 등불 지목은 힌트에 맡긴다.
- `deadCells` = `blocked.map(b => b.cell)` (호환용).
- **누구 탓인가(라운드 5)** — 라운드 4에서 8/8이 "J-16에서 등불 5개 + 돌 3개가 나열됐다"(`C2, G2 (light from A1 F3 D4 B6 E6; rocks G1 C3 G3)`,
  실제 범인은 A1 하나), Priya·Sophie·Denise가 "J-12의 2(D4)가 ⊘인데 막힌 칸 표시가 없다". **틀린 등불** = 레벨의 유일 해에 없는 놓인 등불
  (손으로 만든 유일하지 않은 판은 처음 찾은 해 기준; 해가 없으면 틀린 등불 없음). 해는 레벨 객체별로 캐시(`levelSolution`), 막힌 칸이나 막힌
  숫자가 있을 때만 계산한다. 위의 원인 목록(`lanterns`/`stones`/`causes`/`by`)은 그대로다.
  - `blocked[].culprits`: 그 칸이 막히는 데 관여한 **틀린** 등불 — 후보 자리를 비추거나, 후보 자리를 막는 찬 숫자 돌을 채우는 등불 — 오름차순.
    대개 1개. 유일 해가 있는 판에서는 비지 않는다(해의 그 칸 등불 자리를 막는 것은 틀린 등불뿐이다). **계약과 다른 점**: `lanterns`의 부분집합만이
    아니다 — 찬 돌(`stones`)을 채운 틀린 등불도 들어간다(예: 1 돌을 틀린 C1이 채워 A1이 막힘 → `lanterns` = [], `culprits` = [C1]).
  - `stuckStones`: 더 이상 맞출 수 없는 숫자 돌, 오름차순. `'cannotReach'`(상태 blocked = ⊘: 남은 합법 빈 이웃 < 남은 필요 수) — 빈 이웃을 비추는
    등불, 빈 이웃 옆의 찬 숫자 돌을 채운 등불, 자기 이웃에 놓인 등불; `'over'`(✗) — 자기 이웃에 놓인 등불. 그중 틀린 등불이 있으면 틀린 것만 남긴다.
  - `culprit`: 지금 가리킬 등불 **하나** — `blocked[].culprits`와 `stuckStones[].lanterns`의 틀린 등불 중 가장 원인이 되는 것(`mostCulpableOf`:
    걷었을 때 풀리는 막힌 칸 + 넘침·⊘에서 벗어나는 숫자 돌 수 → `recent`의 가장 최근 → 푸는 충돌 수 → 칸 번호). 관여한 틀린 등불이 없으면 `null`
    (모든 등불이 해에 있으면 막힌 칸·막힌 숫자 자체가 없다).
  - 회귀(라운드 4 실제 상태, 테스트 고정): J-16 E6 C5 C7 B6 D4 F3 A1 → `blocked` C2·G2, 각 `culprits` = [A1], `culprit` = A1;
    J-12 A3 A5 B4 D1 C2 E2 → `blocked` = [], `stuckStones` = [{ D4, cannotReach, [E2] }], `culprit` = E2; J-12 A3 A5 B4 D3 E4 D5 → D4 `over` [D5].
  - 힌트의 `removeWrong` 순위도 같은 함수다(⊘에서 벗어나는 숫자 돌을 점수에 추가했다).
- 라운드 2 "숫자는 다 맞았는데 어두운 칸, Dead cells: none" 보고(Lisa W-8)는 세션 로그상 그 시점 `dead` = 1이었다(페르소나 오독).
  숫자 돌 판정은 이미 들어 있었고, 빠져 있던 것은 **원인 표시**였다 — 이제 `stones`로 어느 돌 때문인지 준다. 회귀 테스트 고정.

### 힌트 (`hintFor`, 문자열 없음)

1. 유일 해에 없는 등불이 하나라도 있으면 `{ kind: 'removeWrong', cells: [하나], remaining }` — **단계적**: 한 번에 하나, `remaining` =
   틀린 등불의 총수(이번 것 포함; 걷을 때마다 1씩 준다). 고르는 기준(가장 원인이 되는 등불): 그 등불을 걷었을 때 풀리는 막힌 칸 수 +
   넘침에서 벗어나는 숫자 돌 수가 가장 큰 것 → 동점이면 가장 최근에 놓은 것(`recent`의 마지막 위치; 없으면 lastMoveCell) → (기록이 없을 때만)
   더 많은 충돌을 푸는 것 → lastMoveCell에 가까운 것 → 칸 번호. 행 우선 순서로 고르지 않는다. 다 걷으면 다음 힌트가 놓을 곳이다.
2. 아니면 현재 보드에서 다시 추론(과거 표시 기억 없음): 찬 숫자 돌 표시(T1) 후
   T1 `stone`(빈 이웃 = 남은 필요 수) → T2 `onlyLight`(어두운 칸을 밝힐 자리가 하나) → 둘 다 없으면 T3: 놓는 즉시 숫자가 깨지거나
   어떤 어두운 칸이 밝힐 길을 잃는 칸을 모두 배제하고 다시 T1/T2 → 그 결과는 `contradiction`(+ `ruledOut`: 배제된 칸, 앵커와 관련된 칸 먼저).
   가장 낮은 단계만 후보, 그 안에서 lastMoveCell에 가까운 것(맨해튼), 그다음 최근 건드린 숫자 돌(`recent` 기록의 최신 칸 옆 숫자 돌)에
   가까운 것, 그다음 앵커와의 거리, 칸 번호. `anchor` = 강제하는 숫자 돌 또는 어두운 칸.
3. 완료(또는 해 없음)면 `{ kind: 'none' }`.

모든 규칙이 건전하고 현재 등불이 모두 유일 해에 있으므로 제안 칸은 해에 속하고 충돌하지 않는다. 추론이 막히면(테스트상 0회)
가장 가까운 남은 해 칸을 `contradiction`으로 준다. 시험: 두 트랙 1–200, 빈 보드·부분 정답 2개·틀린 등불 1/2/3개 상태에서
힌트만 반복 적용(토글 기록을 `recent`로 전달) → 항상 완료, 충돌 0, removeWrong은 항상 틀린 등불 하나이고 `remaining`이 1씩 줄어든다,
gentle은 contradiction 힌트 0회.

하네스(`tools/play.ts`, 라운드 5): 막힌 칸은 걷을 등불 하나 — `Stuck: B3 — take back A1`, 같은 등불 탓인 칸은 묶는다
(`Stuck: C2, G2 — take back A1`; `culprit`의 묶음 먼저, 다른 칸은 그 칸의 `culprits` 중 가장 원인이 되는 것). 틀린 등불이 관여하지 않을 때만
짧은 원인 `Stuck: B3 (light from E1; rocks A3 C3)`. 막힌 숫자는 줄마다 `Stuck number: D4 (2) — take back F2`(없으면 줄 없음; 틀린 등불이 없으면
`— not enough free sides left` / `— too many lanterns touch it`). 걷기 힌트는 `Take back the lantern at B2 (1 of 3)`. **메시지(힌트·수 결과·ILLEGAL)는
보드 위 맨 처음에** 찍는다(라운드 4에서 범례 아래 힌트를 놓쳤다). 데일리: `new --mode daily --date YYYY-MM-DD --variant <코드>`(숫자 돌 코드 P/J/W 등 —
모두 같은 `levelForDaily` 판; `--track`은 거절). 세션 기록에 `stuckNumbers` 개수가 추가됐다.
블라인드 코드 J/W(`playtest/variants2.json`)는 그대로 갱신된 트랙을 가리킨다.

도구: `npm run gen:stats:pips -- --track gentle|deduce --count 300 [--levels]`, `npm run depth -- --variants PG,PD --levels`,
`npm run play -- new --variant P --track gentle|deduce --index n`.

## 데일리 번호·공유 문구 (`share.ts`)

- `dailyNumber(d)` = dayNumber(d) − dayNumber(`DAILY_EPOCH`) + 1 (정수, 윤년 포함). 2026-11-01 = #1, 2027-01-01 = #62.
- 달 모양: 평균 삭망월 29.5306일(1/10000일 단위 정수 `SYNODIC_E4` = 295306), 기준 삭 2000-01-06 18:14 UTC, 그날 정오 UTC의 위상을 8등분
  → 🌑🌒🌓🌔🌕🌖🌗🌘. 경계 근처에서 하루 어긋날 수 있다(테스트: 2024-01-11·2024-04-08 🌑, 2024-01-25·2026-11-24 🌕).
- `shareText(level, r, opts?)` (라운드 5, R2): 3줄. ① `APP_NAME #번호 달` ② 힌트 0회면 `✨`, 힌트 > 0이면 `💡n`(되돌리기는 기호에 영향 없음), `opts.showTime`(기본 true)일 때만 `⏱ m:ss`, `🔥연속` — 공백으로 잇는다.
  ③ (R2, 결정 A5 — **의도한 공유 형식 변경**) 그 데일리의 링크 `dailyLink(n)` = `https://humsleep.github.io/duskwick/<n>?ct=share`.
  `ct=share`는 App Store Connect·웹 리퍼러에서 채널을 가르는 캠페인 토큰이다(개인정보 없음). 에포크 전(n ≤ 0)에는 번호 없이 `…/duskwick/?ct=share`.
  주소는 `DAILY_URL_BASE`, 토큰은 `SHARE_CT`(다른 채널은 `dailyLink(n, "tiktok_bio")`처럼 쓴다). 유니버설 링크·AASA 게시 절차는 `docs/web/README.md`.
- **기호의 뜻(라운드 6, 코드 그대로)**:

  | 기호 | 뜻 | 나오는 조건 |
  | --- | --- | --- |
  | `#n` | 데일리 번호 | 항상(`dailyNumber`, 2026-11-01 = #1) |
  | 🌑🌒🌓🌔🌕🌖🌗🌘 | 그날의 달 모양(장식, 판과 무관) | 항상(`moonPhase`) |
  | ✨ | **힌트 없이 풂** (되돌리기는 평범한 플레이라 상관없음, 결과 화면의 ✨와 같은 뜻) | `hints === 0` |
  | 💡n | 힌트 n회 사용 | `hints > 0` (✨와 함께 나오지 않음) |
  | ⏱ m:ss | 푼 시간 | `opts.showTime`(기본 true)일 때만 |
  | 🔥n | 연속 일수 | 항상 |
  | `https://humsleep.github.io/duskwick/n?ct=share` | 그 데일리의 링크(앱이 있으면 유니버설 링크로 오늘의 데일리가 열린다) | 항상, 마지막 줄 (R2) |

  - 글자는 `APP_NAME`과 **마지막 링크 줄**에만(R2에서 링크 줄만 예외로 풀었다. 테스트: 마지막 줄이 정확히 `dailyLink(dailyNumber(date))`이고, 그 위 줄들에는 `APP_NAME` 밖에 [A-Za-z] 없음, 칸 이름·판 텍스트·🟨 없음, ≤ 4줄). 음수·NaN·소수 입력은 0 / 버림으로 정리, 시간은 599:59에서 멈춘다.

## 데일리 고정 (R2, 결정 A9)

**출시 뒤에는 어떤 날짜의 데일리도 바뀌지 않는다.** 구버전 앱·새 앱·웹 데일리가 같은 #n에서 같은 판을 보여야 공유가 성립한다.

- `fixtures/lanterns-pips/daily-freeze.json`: `DAILY_EPOCH`(#1)부터 400일 이상의 `levelForDaily` 판. 날짜마다 `rows`(`levelRows()`를 "/"로 이은 글자: `.` 바닥, `#` 돌, `0`–`4` 숫자 돌)와 그 ASCII 바이트의 FNV-1a 32(`fnv`, 8자리 hex), 파일 전체 `fnvAll`. 포트(C#·웹)는 이 파일을 그대로 통과해야 한다.
- `tests/lanterns-pips/dailyFreeze.test.ts`가 매 `npm test`에서 전부 비교한다(약 1 s). 깨지면 생성기·규칙 변경이 과거나 미래의 데일리를 바꾼 것이다.
- **파일을 다시 만들지 않는다.** `npm run fixtures`는 이 파일을 건드리지 않는다. `npm run fixtures:daily`(`scripts/dailyFreeze.ts`)는
  - 인자 없이: 파일이 없을 때만 400일을 만들고, 있으면 모두 일치하는지 보고한다(다르면 실패, 덮어쓰지 않음).
  - `--extend N`: 뒤에 날짜를 덧붙이기만 한다(기존 항목은 일치해야 함). 출시 1년이 다가오면 늘린다.
  - `--recut YYYY-MM-DD --i-know`: **의도한** 생성기 변경. 그 날짜 이후 항목만 다시 고정하며, 날짜는 오늘 + 30일 이후여야 한다.
- 생성기를 꼭 바꿔야 할 때의 절차(CLAUDE.md 픽스처 규칙과 같다): ① 먼저 이 테스트가 왜 깨졌는지 확인한다. ② 데일리는 그대로 두고 트랙만 바꿀 수 있는지 본다(`DAILY_GENERATOR_VERSION`과 데일리 시드 키는 트랙과 따로다). ③ 정말 데일리를 바꾼다면 `DAILY_GENERATOR_VERSION`을 올리되 **전환일**(오늘 + 30일 이후)부터만 새 생성기를 쓰게 분기하고(`dailyParams`가 날짜로 버전을 고른다), 앱·웹을 그 전에 함께 배포한다. ④ `--recut <전환일> --i-know` 후 diff를 검토한다. 전환일 이전 항목이 하나라도 바뀌면 그 변경은 기각한다.
