## 2. 마을 열기 시간 — G5 "p75 ≤ 400 ms", 대기 fps 20

방법: `playtest/perf/village-open.mjs` (CPU ×4, 탭 → 마을 첫 표시 프레임, 장면이 직접 `[village] open N ms`로 보고). 실행마다 새 컨텍스트. "첫 열기" = 그 실행의 첫 열기, "다시 열기" = 같은 실행의 두 번째.
시계 기준: 스크립트는 `ready && idle`(내비게이션 후 약 1.3 s)부터 지연을 센다. 지연 D는 대략 "실행 후 1.3 s + D"에 탭한다.

| 조건 (n) | 첫 열기 median / p75 (ms) | 다시 열기 median / p75 (ms) |
|---|---|---|
| **cur, 실행 직후 (D=2.5 s, 프리웜 전)** (15) | **1207 / 1223** | 58 / 63 |
| base `c5c1fc7`, 실행 직후 (15) | 1146 / 1194 | 59 / 61 |
| cur, D=5 s (10) | 1213 / 1233 | 61 / 63 |
| cur, D=8 s (15; 프리웜 타이머 8 s 직후) | 116 / 119 (이상치 2개: 1478, 1306) | 60 / 62 |
| base, D=8 s (15) | 114 / 118 (이상치 2개: 1026, 1167) | 58 / 63 |
| cur, D=9 s (10) | **116 / 118** | 61 / 66 |
| cur, D=12 s (10) | 123 / 129 (이상치 231, 248) | 60 / 66 |
| cur, D=16 s (10) | **116 / 117** | 60 / 61 |

- **프리웜이 끝난 뒤**(돌아온 플레이어는 실행 후 약 10 s부터) 첫 열기 p75는 117–129 ms로 목표 400 ms의 약 30 %다. 다시 열기는 약 60 ms.
- **프리웜 전에 탭하면 약 1.2 s**다 (data 500–570 ms + build 590–600 ms: 청크 로드, 저장·키트 로드, 배경 굽기·래스터). 이전 기록의 564 ms보다 2배 느린데, 저전력 모드 1.56배를 감안해도(≈880 ms) 그보다 느리다. 프리웜 구간은 실행 후 약 6.5 s(미완) ~ 9.5–10.5 s(완료) 사이에서 갈린다. 첫 실행 플레이어는 프리웜이 20 s에 시작한다.
- base(`c5c1fc7`)와 cur는 같은 모양이다 (회귀 없음).
- 판정 **G5 마을 열기: INCONCLUSIVE (실기기 필요), 단 위험 신호 하나.**
  - 프리웜 이후 경로는 대리 측정에서 PASS (p75 117–129 ms).
  - **프리웜 전 경로는 대리 측정에서 FAIL (p75 ≈ 1.2 s)**. 실행 직후 약 10 s 안에 마을을 누르는 플레이어(앱을 열자마자 우편함을 확인하려는 돌아온 플레이어)가 해당한다. 기기에서 같은 구조라면 400 ms를 넘길 가능성이 높다.
  - 완화 후보(구현 변경이라 이번엔 하지 않음): 프리웜 시작을 8 s보다 앞당기기, 또는 프리웜 전 탭에는 열기 전환(페이드)을 먼저 보여 주고 굽기를 그 뒤에 하기.

### 대기 프레임 (거버너)
방법: `idle2.mjs` = `apps/client/scripts/measure-idle.mjs`의 사본에 village·room·market·drawer 화면(최악 시드, 겨울 밤)을 추가. 20 s 무입력. 같은 빌드에서 거버너를 끈 빌드(`VITE_IDLE_GOVERNOR=off`)를 비교.

**60 Hz 렌더 (headless shell, rAF 61/s, 화면당 n=1):** 거버너 켬 = **20.0 renders/s**와 20.0 frames/s — board, town, village, room, market, drawer 전부 정확히 20. 끔 = 60 (board, village). 이 모드는 소프트웨어 래스터라 CPU 열은 비교하지 않는다.

**GPU 프로세스가 있는 Chromium (저전력 모드로 30 Hz 제한, n=2 평균):**

| 화면 | 켬 renders/s | 끔 renders/s | task ms/s 켬 / 끔 | renderer+GPU CPU ms/s 켬 / 끔 | 변화 |
|---|---|---|---|---|---|
| board | 15.1 | 30 | 51 / 71 | 144 / 222 | −35 % |
| town (골목) | 15.0 | 30 | 31 / 43 | 156 / 204 | −24 % |
| village | 15.0 | 30 | 36 / 49 | 174 / 248 | −30 % |
| room | 15.0 | 30 | 29 / 48 | 157 / 238 | −34 % |
| market | 15.0 | (측정 안 함) | 31 | 161 | |
| drawer | 15.0 | (측정 안 함) | 32 | 164 | |

- 30 Hz 화면에서는 앰비언트가 vsync 배수로 맞춰져 20 → 15 fps가 된다 (끔 30 → 켬 15, 정확히 절반). 60 Hz 기기에서는 20이다. 저전력 모드의 iPhone도 비슷하게 30 Hz가 될 수 있으니 기기 측정 때 확인할 것.
- 마을·방·장터·서랍 모두 렌더가 앰비언트 속도로 내려가고, 거버너가 켜진 마을은 꺼진 마을보다 renderer+GPU CPU가 약 30 % 적다.
- 대기 뒤 첫 탭 → 렌더는 켬 5–9 ms(60 Hz 모드), 26–28 ms(30 Hz 모드: vsync 한두 틱). 다섯 번째 탭에서 160–220 ms 한 번이 보이는 것은 `idle-governor.md`에 이미 있는 주기 작업이다.
- 판정 **G5 대기 20 fps: PASS (Chromium 60 Hz 대리).**

## 3. 메모리 — G4

방법: `memory.mjs`. 최악 시드(`worst-village.json`: 2026-12-20 22:00 = 겨울 밤, 주민 7명, 14 lit days, 방 14칸 + 러그, 부탁 3개). 상태마다 (a) Phaser 텍스처 합(모든 텍스처 소스의 폭×높이×4 B), (b) V8 힙(GC 뒤 `Runtime.getHeapUsage`), (c) CDP memory-infra 덤프(`Tracing.requestMemoryDump`, detailed): 렌더러의 `canvas` 할당자, GPU 프로세스의 `gpu/shared_images`·IOSurface, 프로세스별 private footprint, (d) `ps` RSS. 상태 사이에 1.5 s 대기. 탭 한 번 = 실제 마우스 클릭. CPU 스로틀은 걸지 않았다(메모리에는 무관).

시나리오: 보드(프리웜 전/후) → 마을 → 장터 → 방(방문자 2명) → 서랍 → 마을 → 보드 → 20회 왕복(마을 → 방 → 서랍 → 나가기) → 방에서 10분 소크.

### 상태별 (1차 실행; 2차 실행은 `memory-cur-soak.json`: 텍스처 합은 동일, `canvas`·GPU 값은 같은 상태에서 최대 +11.5 MB 차이(캔버스 해제가 지연되는 노이즈), 상태 사이의 차이는 같음)

| 0a 보드, 프리웜 전 | 58.0 | 96.2 | 123.4 | 70.8 / 198.0 |
| 0b 보드, 프리웜 후 | 58.0 | 101.4 | 127.2 | 64.5 / 168.7 |

- **마을 구간이 더하는 텍스처 최대치 = +19.1 MB** (77.1 − 58.0, 장터 오버레이 5.1 MB와 서랍 7.4 MB가 포함). 렌더러 `canvas` +19.1 MB, GPU `shared_images` +19.6 MB로 세 방법이 일치한다. 서랍 탭 5개를 모두 눌러도 더 늘지 않는다 (서랍 안 최대 72 MB, 장터를 안 거친 경로 기준).
- **예산 비교**: 문서의 "마을 청크 텍스처 ≤ 40 MB" 대비 19.1 MB (48 %). `estimateVillageBytes`의 @2x 최악 추정 35.7 MB보다도 작다 (엽서 PNG 5.8 MB 일시 버퍼는 이 시나리오에 넣지 않았다).
- **떠난 뒤 해제**: 텍스처 58.0 MB, `canvas` 101.4 MB, GPU `shared_images` 127.2 MB로 **프리웜 후 보드와 정확히 같은 값으로 돌아온다**. 20회 왕복 뒤에도 같다 (텍스처·캔버스·GPU 증가 0).
- 프리웜이 남기는 몫: 0a → 0b에서 `canvas` +5.2 MB (문서의 "배경 사본 1장 ≈ 5 MB"와 일치), Phaser 텍스처 표에는 안 잡힌다.
- footprint 열은 노이즈가 크다 (같은 상태에서 렌더러 ±8 MB, GPU ±10 MB). 최고점 − 프리웜 후 보드: 렌더러 +13.9 MB, GPU +30.6 MB, **합계 약 +44.5 MB** (소크 실행에서도 +44.7 MB). 숫자는 G4의 "WebContent 증가 ≤ 60 MB"와 같은 지표가 아니다 (iOS의 WebContent 대 GPU 프로세스 분담이 다르다).
- V8 힙: 6.9 → 9.4 MB로 20회 왕복 동안 +1.2 MB(회당 약 0.06 MB 선형). 작지만 단조 증가다. 20회 이후 평탄한지는 소크 쪽에서 9.3 → 9.5 → 9.5 → 9.0 MB로 평탄하게 보인다.
- **10분 소크 (방, 대기 거버너)**: 텍스처 63.9 MB 고정, GPU `shared_images` 133.3 MB 고정, V8 9.0–9.5 MB, 렌더러 `malloc` 40 → 41 MB, `partition_alloc` 72–73 MB. 나가면 58.0 MB로 복귀. 렌더러 RSS(`ps`)는 267 → 281 MB(+14 MB/10 min)로 늘었지만 할당자 어느 쪽도 늘지 않았고 footprint는 70–73 MB로 평탄하다. 측정 때마다 추적 세션을 시작하는 것(렌더러 페이지 잔류)의 영향일 가능성이 크지만 확정하지 못했다.

판정:
- **G4 텍스처 ≤ 40 MB: PASS** (19.1 MB).
- **G4 해제/누수 (20회 왕복, 10분 소크): PASS (Chromium 대리)** — 텍스처·캔버스·GPU 증가 0, V8 +1.2 MB.
- **G4 "WebContent 증가 ≤ 60 MB, jetsam 0" (3 GB 기기): INCONCLUSIVE.** Chromium에서 렌더러+GPU footprint 합 +45 MB (노이즈 ±10 MB)라 방향은 좋지만, WKWebView의 WebContent 수치와 jetsam은 실기기에서만 나온다.

## 5. 아직 실기기(iPhone)가 필요한 것
1. 콜드 스타트 p75 절대값(≤ 1.0 s)과 마을 유무 A/B — Release 빌드(m1), 실기기 M1 20회. 이 측정은 e2e 빌드와 저전력 모드 Mac이다.
2. 마을 열기 p75 두 경로 — **프리웜 전(실행 직후 약 10 s, 첫 실행은 20 s까지)**과 후. 대리 측정의 1.2 s가 기기에서도 나오는지.
3. 3 GB 기기(XS·11·SE2/3급) WebContent + GPU 프로세스 증가 ≤ 60 MB, 20회 왕복 + 10분 소크, jetsam 0. WKWebView 캔버스 총량 상한은 이 대리 측정으로 알 수 없다.
4. 대기 fps/전력: 60 Hz·ProMotion·저전력(30 Hz)에서 20/15 fps가 실제로 나오는지, 열 상태.
5. 엽서 PNG 생성 시 일시 메모리(1080×1350, 5.8 MB 추정)는 이번 시나리오에 넣지 않았다.
